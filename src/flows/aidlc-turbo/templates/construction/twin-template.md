# Twin template

The automated twin of one manual test case. Written by the test writer (the `test-cases` skill), only
when `codebase.has_ui` and `codebase.playwright` in `.specs-aidlc-turbo/repo/repo.yaml` are both true
and at least one step of the Steps or the Regression check runs on a screen. The story's
`surface` never decides it: it says where the code lives, not where the tester looks. It runs against
the application finish already started.

Path: `{codebase.playwright_test_dir}/aidlc-twins/{intent-slug}-{story-slug}.spec.ts`
Use the `.spec.js` variant when the project has no TypeScript. Only the test writer writes in
`aidlc-twins/`, and only its own twin.

## Rules

- Written in the record's language, as the test case is: the test titles and the comments take the
  words of `testCase` in its string table (`node .specsmd/aidlc-turbo/scripts/lib/lang.cjs {code} --show testCase`).
  The skeleton below is in English: `// Step n:`, `// Regression n:` and `, regression` take the
  words of that table.
- One `test` for the Steps, mirroring them one to one, plus one `test` for the
  Regression check when the twin can run any of its steps. Never a suite of variants.
- One comment per step, naming its number: `// Step n:` in the first test, `// Regression n:` in the
  second, so a reader can hold the twin and the test case side by side.
- Assertions come from the `Expected result`, in the same order. In the second test they come from
  what each regression step says the tester must still see.
- Selectors follow the project's own convention: a role or a test id first, the visible label
  from the Steps as the fallback. Never a brittle CSS path.
- Assert structure, state and text. Never appearance: no screenshot comparison, no colour, no font.
- Setup and checks in the database or a log go through the means the project's own twins or tests
  already use: a database client, an API call, reading the log file. Never a new dependency.
- A step the twin cannot automate stays manual: the test case names it under
  `Not covered by the twin`, with why.
- No test data created inside the spec that the Preparation did not describe.
- The spec changes only its own records, the ones the Preparation names with the story's unique key, and cleans up only those, so twins can run in parallel. Serial mode only when the test case names another case that shares its records.

## Skeleton

```ts
import { test, expect } from '@playwright/test';

// Twin of {intent_dir}/tests/US-{SSS} - {story title}.md
// Story: {intent_dir}/stories/{SSS}-{story-slug}.md
// Generated by AI-DLC Turbo construction. Regenerated when the test case changes.

test('US-{SSS} {story title}', async ({ page }) => {
  // Preparation: {the precondition this twin can set up itself}
  await page.goto('{start route}');

  // Step 1: {step 1 in the tester's words}
  await page.getByLabel('{exact label}').fill('{value}');

  // Step 2: {step 2 in the tester's words}
  await page.getByRole('button', { name: '{exact button label}' }).click();

  // Expected result, step 2
  await expect(page.getByText('{exact message}')).toBeVisible();

  // Step 3: {step 3 in the tester's words}
  // Expected result, end
  await expect(page).toHaveURL(/{expected route}/);
});

test('US-{SSS} {story title}, regression', async ({ page }) => {
  // Regression 1: {regression step 1 in the tester's words}
  await page.goto('{route of the place it checks}');
  await expect(page.getByRole('tab', { name: '{exact tab label}' })).toBeVisible();

  // Regression 2: {regression step 2 in the tester's words}
  await page.getByRole('button', { name: '{exact button label}' }).click();
  await expect(page.getByText('{what the tester must still see}')).toBeVisible();
});
```

## After writing

Run the spec once, against the URL finish passed; never start the application for it.

- Every test in it passes: `twin_result: passed`.
- The application does not answer (a connection refused, a base URL that does not answer, a timeout
  on the first navigation): `twin_result: unreachable`, never `not_run`. Finish restarts the
  application and dispatches the writer again to run the twin.
- An assertion fails: `twin_result: failed`, reported at finish.
- `twin_result: not_run` only when no twin was written, when `url` is `none`, or when the project's
  Playwright config has a `webServer` that would start the application. Then the spec does not run.

The story's `### Build notes` holds one twin line, replaced on every run and never appended:
`- **Twin**: {twin path}, {twin_result} ({time of the run})`.
