# Handoff: `run.cjs review --item` prints its two reviewer dispatches through the 30-line cap every plain answer gets, so the first review of an item with many criteria loses the end of the quality dispatch, its standards lines and its `write` path among them

Row 0bn. Met on the first host on 2026-11-24 and 2026-11-25 on Delta, at the first reviews of two items of one intent, on the build installed there, `a8873ebb`. The tip holds the same `src/`.

## What is wrong

`S/` below is `src/flows/inferno/agents/orchestrator/skills/orchestrate/scripts/`.

1. **Every plain answer is cut at 30 lines.** `finish` (`S/run.cjs:267-273`) prints each step's lines through `capLines` (`S/run-lib.cjs:444-448`), which keeps 29 lines and puts `... n more lines` in place of the rest. Its comment says what the cap is for: "Keep any human answer inside the 30-line budget the orchestrator reads."
2. **A review owed is two dispatches, not an answer to shorten.** `owed` (`S/run-review.cjs:100-131`) prints a header, the contract lens's dispatch, the quality lens's dispatch, the one-message line (`ONE_MESSAGE`, `S/run-review-quality.cjs:47`) and the record call. The orchestrator copies each dispatch into a reviewer's prompt and runs the call. Every line is needed, and the cap cuts from the end, where the quality dispatch sits.
3. **Its length grows with the item and the host.** A first review prints one line per acceptance criterion in the contract dispatch (`S/run-review.cjs:176`), and one line per rule file and per lint command in the quality dispatch (`qualityBody`, `S/run-review-quality.cjs:124-136`). The whole is 15 + R + N + S + L lines: N criteria, S rule files that apply to the item's paths, L commands under `verification.lint`, and R one when the real-app line prints. A lens whose paths go to a paths-file (more than 40 paths, `S/run-review-span.cjs:96`) adds one more. On the first host S is 6, L is 0 and R is 1, so the answer is 22 + N lines. At 9 criteria the one-message line and the record call are cut. At 10 the quality `write` path goes too, and each criterion after that cuts one standards line more. At 20 the whole quality dispatch is gone, and at 21 the contract's own `write` path.
4. **The record still waits for the lens it cut.** `owed` notes both lenses as dispatched before it prints (`lens.noteDispatched`, `S/run-review.cjs:117`), and the record waits for every noted lens (`lensesWaiting`, `S/run-review.cjs:215-220`). From 20 criteria on, the record waits for a quality dispatch the orchestrator never saw.
5. **The JSON answer is whole and the plain one is cut.** `--json` prints the payload uncut, with the quality lens's `standards`, `lint` and `write` under `quality` (`S/run-review.cjs:121`, `:166`). The orchestrator runs the plain form.

## How to fix

1. **A dispatch prints whole.** A step result that carries a dispatch the orchestrator forwards is never cut. `owed` (`S/run-review.cjs:119-130`) returns `whole: true`, and `finish` (`S/run.cjs:271`) prints `result.out` as it is when `result.whole` is set. The cap stays for every other answer, the lists it was written for. Read the other answers that carry a reviewer dispatch, the intent review's (`S/run-intent-review.cjs:94-109`, one `settled` line per settled item) and the record's reprint of a lens still waiting (`lensesWaiting`), and set the same mark where their lines can pass 30.
2. **The test.** In `S/run-review-quality.test.cjs`, with the fixture of `S/run-review-quality-fixture.cjs`: an item spec with 20 acceptance criteria and a host standards block of six rule files that all reach its paths. Plain `run.cjs review --item` exits 3. `block(out, <quality agent>)` holds the six `standards` lines and ends with the quality `write` line, and the one-message line and the record call follow it. No line ends in `more lines`. The cap's own pins (`S/run-gate-marks.test.cjs:108`) stay green.

## Until it is built

When `review --item` ends in `... n more lines`, the session runs the same call again with `--json` at once, before it dispatches. With no lens file written yet, a second call at the same HEAD takes the same path and notes the same ranges. The session gives the quality reviewer the `standards`, `lint` and `write` of the payload's `quality` object, sends both dispatches in one message, and runs the record call it always runs. It never copies those lines from another item's dispatch: the rule files follow each item's own paths, and on the first host an item that changes only `definitions/` gets two of the six.
