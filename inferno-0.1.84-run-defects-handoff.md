## 15. An item that moves a file with `git mv` never gets a current proof, so its review is refused forever

**What is wrong.** `verify-item` writes the proof's paths from `changedPaths` (`S/run-gate.cjs:56-60`), which runs `git diff --name-only <since>` with git's default rename detection, so a moved file lists only its new path. `proofAtHead` (`S/run-item-proof.cjs:154-156`) lists what changed with `--no-renames`, so the old path shows up as a deletion that the item owns and the proof does not carry. Every `run.cjs review --item` then answers `verify-item owed ... was taken over an older state of its paths`, and `verify-item` writes the same proof again: a loop with no way out for any item whose spec asks for a `git mv`.

**Evidence.** Skoft_CRA, intent `the-lower-layers-stop-calling-up`, item `llu-process-facts-sit-below-the-store`, 2026-11-15, flow build f3be640a. The item moves `src-tauri/src/shell/child_env.rs` and `child_env_tests.rs` to `src-tauri/src/process/`. The proof's `diff.paths` held 29 paths; `git diff --name-only --no-renames <from> HEAD` held 31, the two extra being the two rename sources. Running `verify-item` with `GIT_CONFIG_COUNT=1 GIT_CONFIG_KEY_0=diff.renames GIT_CONFIG_VALUE_0=false` in its environment wrote a proof with all 31 paths, and `review` then printed the reviewer dispatch. That is the host's workaround.

**How to fix.** Make both readers list a move the same way: `changedPaths` passes `--no-renames` (a move then names both sides, which `itemFiles`, `sinceOutside` and the lane scopes all want: the old path's scope is what picked the journeys before the move). `hashOf` and `headDiffHash` already pass `--no-renames`, so the hash needs no change. Test: a scratch repo where the item `git mv`s an owned file, `verify-item`, then `review --item` prints the dispatch, not `verify-item owed`.


## 16. A rule file under `.specs-inferno/standards/` counts as ledger, so an item that delivers one can never prove it

**What is wrong.** The host's rule files live under `.specs-inferno/standards/`, and `standards:` in the host config hands them to every builder and reviewer as rules to follow. They are deliverables a work item writes, not bookkeeping. But every ledger test reads the whole `.specs-inferno/` tree as ledger: `inLedger` (`S/run-item-proof.cjs:85`) leaves the file out of the item's proof, so the review dispatch's `paths` line omits it and a later change to it leaves the proof current. The recorder refuses a mutant on it (`S/run-review-file.cjs:328`, "a mutant breaks the code, never the ledger") and refuses a pin that names it (`S/run-review-file.cjs:292-293`, "a pin reads the code, never the ledger"). So a criterion whose only product line is in a rule file has no mutant and no pin, and no route the flow accepts to prove it.

**Evidence.** Skoft_CRA, intent `every-agent-gets-the-tool-that-fits-the-file-it-touches`, 2026-11-14 and 15, flow build f3be640a. Item `tft-ast-grep-is-the-structural-search-of-the-reading-roles` creates `.specs-inferno/standards/tooling.md` (commit e826a418a). Its review dispatch printed `range 9de79cdf1..e826a418a paths docs/SEARCH.md scripts/tooling-docs.test.mjs`, without the new rule file. The first `run.cjs review --item ... --reviewer ... --quality-reviewer ...` exited 2 with:

```
ERROR [BAD_REVIEW] .specs-inferno/intents/every-agent-gets-the-tool-that-fits-the-file-it-touches/reviews/tft-ast-grep-is-the-structural-search-of-the-reading-roles.yaml: mutants entry 2 breaks .specs-inferno/standards/tooling.md; a mutant breaks the code, never the ledger. send this back to the reviewer that wrote the file, then run the same command again.
```

The reviewer turned the mutant into a pin on `tooling.md`, which `S/run-review-file.cjs:293` refused too, so it dropped both. The item's criteria 2 and 3 (what was refused is on record, the rule file follows the standards format) are recorded with no mutant and no pin. The next item, `tft-cargo-nextest-is-measured-before-it-is-adopted`, has the same gap for its criterion 5 (the record in `tooling.md` holds both numbers and one decision). The host's workaround is that a test reads the rule file and the gate marks the criterion. Nothing catches a later edit of the file that breaks that test's subject, until the next gate.

**How to fix.** Make the ledger `.specs-inferno/` minus `.specs-inferno/standards/`: one `lib.inLedger(path)` in `S/run-lib.cjs` that answers false under `standards/`, used by `S/run-item-proof.cjs:85`, `S/run-review-file.cjs:194`, `:292` and `:328`, and by the grant refusal in `S/run-grant.cjs:74` so a builder may be granted a rule file. State, config, intents, reviews and archive stay ledger. Test: a scratch repo whose item owns `.specs-inferno/standards/x.md`. Its proof lists the file, a mutant on it is run and caught by a test that reads it, and a pin on it is checked.

## 17. A command whose verdict depends on the merge base reuses a green minted at another base

**What is wrong.** `commandProof` (`S/run-proofs.cjs:133-139`) keys a green on `[command, config file, scopeHash]`, and `scopeHash` (`S/run-proofs.cjs:26`) hashes only the head's files in the command's `finalize_scopes`. One cache holds the proofs for every worktree of the host and keeps them all. A ratchet whose verdict is the head's count against the merge base's count (here `node scripts/lint-ratchet.mjs <check> --base main`) is therefore green at a later base whenever the scoped head content matches an earlier green, though its base count has changed. The flow already knows the shape: it never proof-caches its own doubles ratchet (`S/run-integrate.cjs:270`). The host has no key to say "this command reads the base": `readConfig` takes none (`S/run-lib.cjs:115-145`).

**Evidence.** Skoft_CRA, intent `every-agent-gets-the-tool-that-fits-the-file-it-touches`, item `tft-the-scope-of-an-item-chooses-its-lint`, 2026-11-15, flow build f3be640a. An oracle ran three landings through the real `run.cjs integrate` and `run-proofs.cjs`, with a spawn stub that counts a.sh against the merge base. L1 rewords a.sh (2 findings against 2 at its base) and is green. L2 lowers it to 0. L3 is `git revert` of L2, so a.sh holds 2 findings against 0 at its base. L3 exited 0 with no spawn of the lint, because it reused L1's proof (same command, same config, same scoped content). With the base written into the command line, L3 spawned once and exited 2. The host cache held 4145 proofs, the oldest from 2026-09-10. Since then main has had 8 revert commits, 3 of them into lint scopes (657491e83, 14b736e01, 0d0b9fa5b). The host fixed its direct-landing path by writing the landing's base into the line it proves. An intent integrate's fixed `--base main` line keeps the hole, and only the flow can close it.

**How to fix.** Let a host mark a command whose verdict reads the base, for example `verification.base_scoped: [<command>, ...]`, read in `S/run-lib.cjs` beside `finalize_scopes`. `commandProof` then adds the merge base sha (`git merge-base HEAD <base>`, as `S/run-since.cjs` resolves it) to the key of such a command. A smaller alternative: never write a proof for a listed command, as the doubles ratchet already does. Test: a scratch host with one listed command and a stand-in that compares a counted file with the merge base. Two landings with the same scoped content at different bases must both spawn, and the second must go red when its base count is lower.

## 18. A criterion that only an integrate command or a one-time measurement proves has no proof kind

**What is wrong.** `gateHeld` (`S/run-criterion-marks.cjs:56`) accepts a mark only for a `verification.finalize` command or a lane. A host that keeps a check in `verification.integrate` and out of finalize, by design, cannot mark the criterion "the check exits 0 on this branch", although integrate runs that check on every integration and refuses red. A one-time measurement (a count on a named commit with a pinned tool) takes neither a mark nor a mutant. And `mutate.checks` read no verdict from a red ratchet run against a base, so even a real mutant on such a check read none. The recorder refuses the clean intent review, and the orchestrator has to invent a workaround.

**Evidence.** Skoft_CRA, intent `every-agent-gets-the-tool-that-fits-the-file-it-touches`, 2026-11-15, the same flow build as section 17. `run.cjs review` refused a clean intent review with BAD_REVIEW for four criteria: three of the form "`node scripts/lint-ratchet.mjs <check> --base main` exits 0 on this branch" and one that three ast-grep queries print the counts a rule file records for a named commit. The host's workaround, on an oracle's decision: a second `mutate.checks` entry for `--base <sha>` (host commit 10b88d762), three mutants whose test is the check against main's sha, and the measurement moved out of the item into the brief's external proof with an evidence file (c5355649b, ac06b6914). A `--base main` mutant test was ruled out, because a test machine's `main` can be stale and the mutant runner never runs the test unmutated first, so a stale base would read as a catch.

**How to fix.** Let `gateHeld` accept a command of `verification.integrate`, and have `S/run-gate-marks.cjs` read its verdict from the green proof `commandProof` (`S/run-proofs.cjs:133`) finds for the gate's tree, once section 17's base key has landed. Have the plan lint send a one-time measurement to the brief as an external success criterion rather than an item criterion. Test: a scratch host with an integrate-only command and a criterion marked with it. With a green integrate proof for the tree the intent review records clean, and without one it is refused.

## 21. The `Tester proves:` reader takes any token with a digit as a case id, and the detached gate checks it only after the lanes start

**What is wrong.** `testerProves` (`S/run-cases.cjs:273-276`) splits the brief's `Tester proves:` line on spaces and commas, strips non-word characters and keeps every token that holds a digit. A path with a line number (`integration/TEST-CASES.md:4752`), a section number or a date in that line becomes a case id that no commit can answer, so the gate is red before it runs a command. The detached gate makes it cost more: `gate --detach` (`S/run-gate.cjs:253-260`) folds, checks the intent review and starts the lanes, but the cases check runs only inside the gate process (`S/run-gate.cjs:156`). The gate dies at once, the smoke and Windows lanes keep running on the remote machines, and a second `gate --detach` after the brief is fixed is refused with `GATE_RUNNING` until both lanes end.

**Evidence.** Skoft_CRA, intent `a-buyer-and-reviewer-prove-the-release`, 2026-11-15. The brief's line read `TC-346 (reserved for ..., stub at integration/TEST-CASES.md:4752)`. The gate result held `"unanswered":[{"case":"integrationTEST-CASESmd4752","file":"integration/TEST-CASES.md","why":"the brief's Tester proves line names it"}]` with `"results":[]`, while `lane-smoke` and `lane-windows` were still running. The host reworded the line to name TC-346 alone and waited for the lanes before restarting the gate.

**How to fix.** Keep only tokens that match the host's case-id shape (`casesConfig` already knows the prefix, for example `/^TC-\d+$/`), and refuse the brief in the plan lint when the line names anything else. Run `cases.refusal` in the detach path beside `intentReview.gateRefusal`, before `lanes.startLanes`, so a red that needs no command never starts a lane. Test: a brief whose `Tester proves:` line names `TC-1` and `x.md:42`. `testerProves` returns `['TC-1']`, and `gate --detach` with an unanswered case exits 2 and starts no lane.

## 19. A gate mark added to a completed item is never checked against the config

**What is wrong.** `run-plan-lint.cjs` refuses a mark whose name `gateHeld` (`S/run-criterion-marks.cjs:56`) does not hold, but it skips completed items. `run-mutant-coverage.cjs:173` then counts any mark that is not late. So an orchestrator that marks a criterion of a completed item in a spec-only commit, for instance `(gate: cargo test --manifest-path src-tauri/Cargo.toml)` on a criterion that command never runs, gets a clean intent review and a gate that prints PASS beside a check that did not happen.

**Evidence.** Skoft_CRA, intent `the-lower-layers-stop-calling-up`, 2026-11-15, flow build f3be640a. Criterion 6 of `llu-the-store-runs-the-evidence-sweep-it-is-given` is a `cargo check --features promo-capture` that no finalize command ran. The oracle rejected marking it with `cargo test` because nothing would have refused that false mark; the host instead added the check to `verification.finalize` and `verification.integrate` (host commit 0e1ac98f4) and marked the criterion with it (e40e0f730).

**How to fix.** Have the mutant coverage (or the intent review's record) run `gateHeld` on every mark it counts, completed item or not, and refuse a name the selected config does not hold, as the plan lint does for an open item. Test: a scratch host with a completed item whose criterion carries a mark naming a command outside `verification.finalize`; recording a clean intent review is refused with that name.

## 20. A mutant whose test is a bare shell check reads no verdict

**What is wrong.** A criterion proved only by a check (a `git grep` count, a probe line, a diff count) can take a mutant whose broken line reintroduces what the check forbids. But the mutant runner reads a verdict only from a test runner's summary, so a test written as the check itself, `test $(git grep ... | wc -l) -eq 0`, exits 1 on the mutant and still reads as no verdict. The reviewer has to wrap each check in an inline `node --input-type=module -e 'import {test} from "node:test"; ...'` so a summary prints.

**Evidence.** Skoft_CRA, intent `the-lower-layers-stop-calling-up`, 2026-11-15, flow build f3be640a. Fifteen check-only criteria (greps, slice probes, `SKOFT_CRA_` diff counts) were proved by mutants; the intent reviewer measured that the bare `test ... -eq 0` form gave no verdict on this host and rewrote all fifteen as inline node tests, which pass unmutated and fail on each mutant.

**How to fix.** Let a mutant name its test as a plain check (a `check: true` key, or a test without a runner summary) and read the exit code: non-zero on the mutant and zero on the unmutated tree, which the runner then runs first, is caught. Test: a scratch tree with a grep criterion, a mutant that adds the forbidden line, and a bare `test $(...) -eq 0`; the record reads caught.


## 22. A stale local base branch makes every synced file the intent's own, so each fold re-owes the intent review

**What is wrong.** `ownReads` (`S/run-intent-fold.cjs:19-26`) lists the intent's files as `<ref>...<at>` for both `base` and `origin/<base>`, and `ownFiles` (`:33`) takes their union. When the local `main` lags `origin/main` (the primary checkout is not pulled while another gate holds it), `main...HEAD` diffs from an old merge base, so every file main synced since then counts as the intent's own. `foldBound` (`:49-66`) then binds each later fold's change to those files, with `review.outside: ["**"]` set to stop exactly that. Every kb sync on main re-owes the intent review before the gate may start.

**Evidence.** Skoft_CRA, intent `a-buyer-and-reviewer-prove-the-release`, 2026-11-15. Local `main` at d83c1ed80, `origin/main` at 644d9e7eb. `git diff --name-only main...HEAD -- grok` listed 8 files and `git diff --name-only origin/main...HEAD -- grok` listed 0; the intent never touched `grok/`. Three gate starts in a row answered `intent review owed ... the fold ... changed what the review binds: grok/...` for kb-only folds, each costing a reviewer round and a restart.

**How to fix.** Diff against the newer of the two refs only: when one is an ancestor of the other, use the descendant (`git merge-base --is-ancestor`), and keep the union only when they have diverged. Test: a scratch host whose local base lags its origin by one commit that adds `kb/x.md`; fold it into the intent, then `foldBound` binds nothing and the gate starts without a review.


## 23. A suite that prints a refusal line in its own output turns a real red into "no verdict"

**What is wrong.** `readRun` (`S/run-check-refused.cjs:71-75`) counts a run as refused when its exit is non-zero and any line of its own log, from where the run started, matches `verification.refused`. A suite whose tests print a fixture refusal line, for example a host's tests of its own wrapper, and that then fails for a real reason, is read as refused. Integrate, the gate and verify-item then report "no verdict, a fault of the test machine", run it once more, and end with exit 5 and "run the step again". A real red is hidden, and the step it names reruns it without end.

**Evidence.** Skoft_CRA, direct integrate of branch `direct-alpha-refuse`, 2026-11-15. `npm run test:definitions` exited 1 with one real failing test (8141 tests, 8128 pass, 1 fail: `scripts/specs-inferno-codex.test.mjs:455`). Its own tests printed fixture lines such as `remote-run: REFUSED [machine] delta: the session holds the machine lock no longer, so this ran nothing; no verdict`. Integrate ended with exit 5: "1 of 5 integrate check(s) got no verdict: the host's wrapper ran nothing, twice, a fault of the test machine and not of the code; run the step again". The log is `~/.cache/specsmd-inferno/Skoft_CRA/direct-alpha-refuse/integrate-20261115T160642Z/2.log`, lines 8488 to 8787 and 9028.

**How to fix.** Read a refusal only where the host's wrapper writes one. Count it only on the host's refusal exit, which Skoft_CRA's config comment names as 75, and only from the run's last non-empty line, never from anywhere in its output. A host key such as `verification.refused_exit: 75` carries the code. Test: a shell that prints a matching fixture line, then fails with exit 1, is a red; one whose last line matches and that exits 75 is refused.

## 24. A count probe that shows 0 reads as drift, because grep exits 1 on no match

**What is wrong.** `measure` (`S/run-probes.cjs:120`) returns `exit <code>` for any non-zero exit, so `run.cjs probes` (`:192-198`) compares a probe's output with its `shows` only when the command exits 0. A probe of the form `grep -c X file` whose plan says `shows: "0"` prints `0` and exits 1, since grep exits 1 when nothing matches. It is then reported as `drift ... expected 0 got exit 1`, although the output is exactly what the plan says. Plan-lint accepts the probe, so the plan carries a probe that can never pass.

**Evidence.** Skoft_CRA, intent `a-journeys-green-moves-only-with-what-it-runs-and-the-testers-own-rules-are-checks`, item `jgm-the-tester-and-the-journeys-are-type-checked`, 2026-11-16. The probe `grep -c tester scripts/tsconfig.checkjs.json` with `shows: "0"` was reported as drift before the item's builder was dispatched, and the orchestrator had to read the drift by hand to tell it apart from a moved tree.

**How to fix.** Plan-lint runs each probe the way `probes` runs it and refuses one whose exit is non-zero while its output matches `shows`, so the planner writes `grep -c X file || true` or `git grep -c`. Or `probes` compares stdout first and reads a non-zero exit as drift only when the output differs too. Test: a probe printing `0` with exit 1 against `shows: "0"` is no drift, or plan-lint names it.

## 25. A sibling's correction to a file two items own fails the other item's proof with a message that names a correction it never had

**What is wrong.** When two items of one intent both own a file, and a correction of one of them changes it after the other's dispatch was accepted, the other item's `verify-item` stops with `DISPATCH_PROOF accepted dispatch bytes changed at <file>: run dispatch-log before a correction resumes the builder` (`S/run-attribute.cjs:100`). The item had no correction. The only way on is a `dispatch-log` with no builder behind it, accepted with the shared path, then the item's delta review of a change it did not make. `integrate` meanwhile refuses with `ITEM_REVIEW_OWED`.

**Evidence.** Skoft_CRA, same intent, 2026-11-16. `jgm-a-selector-src-drops-fails-the-unit-gate` and `jgm-a-lane-names-the-tester-changes-main-took-under-its-walk` both own `docs/TESTING.md`. The lane item's correction `e2b0757a9` (its `Item:` trailer names the lane item) changed the file. The selector item's integrate then refused, and its `verify-item` gave the DISPATCH_PROOF line. The empty dispatch `78491fe4-3ef7-4353-b7f8-20e5985a24c0` and two delta reviews of range `068b02062..3ad4b65cc` cleared it. Both reviews read only the sibling's paragraph and were clean.

**How to fix.** When the bytes of an accepted path changed, `verify-item` reads the `Item:` trailer of the commit that changed them. When it names a sibling, it takes the proof again itself and says the item's review is owed for that range, with no new dispatch. The DISPATCH_PROOF line stays for bytes no item's commit explains. Test: two items owning one file, a committed change to it carrying the other item's trailer, gives a fresh proof and an owed review, never DISPATCH_PROOF.

## 26. A delta reviewer whose verdict still holds leaves its file unwritten, and the record refuses it

**What is wrong.** A delta review whose earlier verdict still stands can leave its review file as it was. The record then refuses: `refusing to record the review of <item>: <file> is not written` (`S/run-review-quality.cjs:186`). The reviewer cannot stamp the file instead, because the schema refuses `commit:` and has no field for a line of reading. The "Delta review" sections of `agents/reviewer/agent.md:31` and `agents/reviewer-quality/agent.md:51` say how to treat each earlier finding, but not that the file must be written again when nothing in it changes.

**Evidence.** Skoft_CRA, same intent, 2026-11-16, the quality review of `jgm-a-selector-src-drops-fails-the-unit-gate`, range `068b02062..3ad4b65cc`. The reviewer answered "clean, the file stays as written", and the record refused. The reviewer had to be resumed only to write the same file again.

**How to fix.** The two "Delta review" sections say a delta review always writes its file again, even when nothing in it changes. Or the record accepts an unchanged file whose verdict is clean and whose earlier findings are all resolved, and stamps the new range itself.
