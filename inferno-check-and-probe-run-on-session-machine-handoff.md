# Handoff: a check mutant and a diagnosis probe run on the session's own machine, and no host key sends them where the host's tests run, so a session hosted where heavy work must not run would run a heavy check or a browser probe there

Row 0bl. Read on the first host on 2026-11-24 in the build installed there, `a8873ebb`, which the tip holds unchanged, while it set up its first session hosted on Alpha, a machine where builds and tests must not run. No run has met it yet: that session starts at or after 2026-11-24 23:00Z.

## What is wrong

`S/` below is `src/flows/inferno/agents/orchestrator/skills/orchestrate/scripts/`.

1. **A check mutant runs in place, bare.** "it runs as written in the tree, under bash, never through the host's `mutate.run`, never in a `mutate.session`, never queued on the machine's build wrapper" (`S/run-mutate-check.cjs:15-17`). Its run on the tree as it is takes `{ wrap: false }` (`:60`), and so does its mutant run (`S/run-mutate-batch.cjs:101`, `wrap: !e.check && !hs.carried`). A check written through the host's wrapper reads no verdict (`placed`, `S/run-mutate-check.cjs:36-38`).
2. **The one host route needs a finding line.** "A host's `mutate.checks` entry is another way: its check runs through the wrapper and reads caught on its finding line" (`:19-20`). A check whose verdict is its exit code, which is what `check: true` says, has no way to the host's test machine.
3. **A diagnosis probe runs in place.** "A diagnosis probe is whatever shows the cause, a browser run included, so it goes bare through the machine's build wrapper with no cap of its own" (`S/run-probes.cjs:108-110`, `measure` at `:112`). No host key places it.
4. **The flow already places an item's own check on the host's machine.** `S/run-item-check.cjs:45-62` puts `verification.run` around a bare check (`wrapperOf` at `:46`, `commandOf` at `:57`), runs it in `verification.session` (`checkRounds`, `:56`) and reads the wrapper's refusal (`readRun`, `:59`, through `S/run-check-refused.cjs:89-94`, which reads `verification.refused` and `refused_exit`). The two placements above use none of it. They assume the session's machine may run every check and probe a plan holds, which holds while sessions run on a test machine and fails for a session hosted where heavy work must not run.

## Evidence

- **The host's session shape.** The first host's Alpha-hosted session sends every build and test to Beta through `remote-run.sh auto`, and its guard denies a heavy command run locally (the host's launch notes, `out/launch.txt` of test-manager's `alpha-skoftapp` folder, 2026-11-24 13:54Z). The guard is a tool hook, so it sees `node run.cjs ...` and never the commands that script runs: a check mutant or a probe passes it unseen.
- **What the host's plans hold** (`git grep` over `.specs-inferno/` on its `main`, 2026-11-24). 47 plan files carry `check: true` mutants. Most of their checks are greps, counts and awk lines, which may run anywhere. The heavier ones: `npm run lint:copy` (11 entries, `node scripts/copy-lint.mjs --worktree`), `node scripts/verify-quotes.mjs` (3), `npm run check:wire` (three node contract scripts) and one `node --test` file. 290 work items carry a diagnosis block. One probe launches WebKit through Playwright (`.specs-inferno/archive/intents/the-carried-lane-reds-go-green/work-items/clr-the-empty-shelf-and-a-fast-check-are-read-as-drawn.md:85`), the browser run the comment names.
- **Found by** the host's test-manager while it set the session up (its ledger, "Alpha as the host of one skoft.app session", 2026-11-24): "Still on Alpha after the package: the flow's worktree bootstrap `npm ci` (once per intent) and mutant `check:` entries with wrap:false." The bootstrap half is the host's own: `worktree.bootstrap` in its config names `npm ci`, and the flow runs what the host lists there (`S/run-worktrees.cjs:124`).

## How to fix

1. **A check mutant is placed as a test mutant is.** With the host's `mutate.run` set and `verification.refused_exit` declared, a `check: true` entry and its run on the tree as it is go through `mutate.run`, and through `mutate.session` when its `match` reaches the placed command, as a test does (`S/run-mutate-session.cjs:67-78`, `:130`). Its verdict stays its exit code: green on the tree and red on the mutant reads caught, green on the mutant a survivor. A refusal read through `S/run-check-refused.cjs` reads no verdict, so the wrapper can never pass for the check's own red. Without `refused_exit` the flow cannot tell a refusal from the check's red, so the check stays in place, bare, as today. `placed` stops marking a check written through the wrapper as WRAPPED when `refused_exit` is declared.
2. **A diagnosis probe is placed as an item's check is.** `measure` with `cap: false` runs the probe through `wrapperOf(config.verification)` and `commandOf`, as `S/run-item-check.cjs:46` and `:57` do, reads a refusal as never answered, and matches `shows` against the wrapped run's output. A `probes:` measurement, a grep or a count under its 60 s cap, stays in place.
3. **The tests.** In `S/run-mutate-check.test.cjs`: with `mutate.run` and `refused_exit` in the fixture config, a check entry runs through the run template (its log carries the template's marker), reads caught on a green tree and a red mutant, and reads no verdict on the refusal exit; without `refused_exit` it runs in place as today. In `S/run-probes-exit.test.cjs`: with `verification.run` set, a diagnosis probe runs through it and its `shows` line is read from the wrapped output, a refusal reads never answered, and a `probes:` measurement still runs in place under its cap.

## Until it is built

A planner there keeps a diagnosis probe to a grep, a count or an awk line.
