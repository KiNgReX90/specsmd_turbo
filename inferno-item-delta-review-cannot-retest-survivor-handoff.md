# Handoff: an item's delta review has neither survivor repair the intent review has, so a survivor whose recorded test cannot reach the case that catches it holds the item at `fix`, whether a correction renamed that case or the first review filed the mutant under the wrong criterion

Row 0bt. Met on the first host on 2026-11-25 on Delta (another test, points 1 to 4), and again on 2026-11-27 on Delta (a withdrawal, point 5), both on the build installed there, `a8873ebb`. The tip holds the same `src/`.

## What is wrong

`S/` below is `src/flows/inferno/agents/orchestrator/skills/orchestrate/scripts/`.

1. **The retest route exists for the intent review alone.** A survivor written again with only `test` changed takes that test and keeps its first one as `was` (`retest`, `S/run-review-mutants.cjs:222-229`). Only `intentMutants` calls it (`:275`). The header places the route in its intent review paragraph (`:32-35`), and the changelog entry of `9b9f3a9b` says "At the intent review".
2. **An item's delta review refuses that entry as new.** `itemMutants` runs `refuseNew` before anything else (`S/run-review-mutants.cjs:116-117`). `refuseNew` (`S/run-review-file.cjs:396-402`) accepts an entry only when `sameMutant` holds, and `sameMutant` needs a test the two entries share (`:318-320`). Its message tells the reviewer to leave mutants out, and the reviewer text says the same (`agents/reviewer/agent.md:33`).
3. **So a survivor's `test` is fixed for the whole item loop.** Every delta record reruns the survivor with the command the first review wrote (`S/run-review-mutants.cjs:118`, `:141`). When a correction renames or moves the case that command selects, the rerun no longer reaches it. A `-g` alternation that still selects other cases stays green and reads `caught: no` on code the corrected case catches. The verdict stays `fix`, and the item cannot go clean while the case name and the recorded command disagree.
4. **The item's own review can ask for that rename.** Here one first review held both: the mutant's test selected the fold case by its name at the time, and a minor finding on the same criterion asked the builder to rename that case so the criterion's own command selects it. The builder did what the review asked, and the next record reran the survivor on the name the rename removed.
5. **An item review cannot withdraw a mutant filed by mistake.** `withdrawn` is an intent review key (`S/run-intent-review-file.cjs:23`), and `withdrawnOf` (`S/run-review-aside.cjs:39-45`) is read only by the intent review file (`S/run-intent-review-file.cjs:20`, `:112`) and by `carryAside` (`S/run-review-aside.cjs:116-124`). An item review has no such key (`ITEM_KEYS`, `S/run-review-file.cjs:23`). So a mutant the first item review filed under a criterion whose command cannot read the line it breaks is carried by every delta record (`S/run-review-mutants.cjs:117-118`), reruns on that command, survives, and keeps the verdict `fix` with a major survivor finding (`:142-146`). Another test would not mend it: the survivor would then count for a criterion whose own command never catches it. The ladder then sends the item to the escalate builder, the oracle and the user (`S/run-review-ladder.cjs:13-16`), though another criterion's test already catches the change. Its only exits are a new reach for that command, a rewrite of the production line, or the user. The intent review has `withdrawn` for this mistake, so the asymmetry is the defect. A survivor whose command should read its line is a different case: it shows a gap in that command, and the command is what gets fixed.

## How to fix

1. **An item's delta review takes the retest route.** In `itemMutants`, call `retest(rel, doc, previous)` before `refuseNew` (`S/run-review-mutants.cjs:116-117`). The survivor then holds the new test with its first as `was`, so `sameMutant` holds through `was` and `refuseNew` passes. The survivor reads `caught: no`, so it is due and runs with the new test (`:118`, `:141`). An entry that changes its criterion, file, line, find or replace stays refused, and so does a caught entry given another test, as in the intent review.
2. **The texts name the route.** `refuseNew`'s message names it for a survivor, as `refuseSecond` does (`S/run-review-mutants.cjs:181-193`). The header paragraph (`:32-35`) says the route holds in an item's delta review too. `agents/reviewer/agent.md:33` gains one sentence: a survivor whose `test` no longer selects the case that should catch it is written again with only `test` changed. The survivor finding's fix (`S/run-mutant-runs.cjs:258`) may say the same for a renamed or moved case.
3. **The test.** Beside `S/run-review-mutants-retest.test.cjs`, on its fixture: an item's first review records a survivor, a correction adds the case that catches it under another name, and the delta reviewer writes the entry again with only `test` changed. The record runs it with the new test, reads `caught: yes`, keeps the first test as `was` and writes `clean`. The same entry with `line` changed, and a caught entry with another test, are still refused as new.
4. **An item's delta review takes `withdrawn`, as the intent review does.** `ITEM_KEYS` (`S/run-review-file.cjs:23`) gains `withdrawn`, with the entry as recorded plus `reason` (`withdrawnOf`'s schema, `S/run-review-aside.cjs:39-45`). In `itemMutants` (`S/run-review-mutants.cjs:115-128`), each withdrawn entry must be one the last record holds (`sameWherever`, as `carryAside` checks at `S/run-review-aside.cjs:116-121`), and the entries it names leave `entries`, so they stop running and write no finding. The record carries the list over, and an entry written under `mutants` again while withdrawn is refused (as `:124` does for the intent review). A withdrawal never counts for its criterion: when no other caught mutant or checked pin answers that criterion, the record prints that the intent review owes it one (`owes`, `S/run-review-mutants.cjs:112`, the line `:119-120` already prints for an entry with no line to break), so a withdrawal never closes a gap (`S/run-review-aside.cjs:6-9`). `owedProposals` (`S/run-mutant-coverage.cjs:101-106`) leaves an item's withdrawn entries out, and the intent review reads their criterion as owed. `agents/reviewer/agent.md:33` gains two sentences. A survivor whose criterion's command should not read the line it breaks was filed by mistake: copy it under `withdrawn`, with a reason that names the criterion whose test catches it. A survivor whose command should read its line is a gap in that command, never a withdrawal.
5. **The test for point 4.** On the same fixture: a first item review records a survivor under criterion 2 whose test does not read the file, while criterion 1's test catches the change. The delta reviewer copies it under `withdrawn` with a reason: the record runs nothing for it, writes `clean` when nothing else is open, prints that the intent review owes criterion 2 a caught mutant or a checked pin, and the intent review's coverage lists criterion 2 as owed. A withdrawn entry that matches no recorded mutant is refused, and so is one written under `mutants` again.

## Until it is built

A correction keeps the case a surviving mutant's `test` selects reachable by that command. A renamed case keeps the old name's words beside the new ones, and a moved case stays in the file the command names. When a finding asks for a rename, the new name carries both phrases.

An item reviewer files a mutant only under a criterion whose own command reads the line it breaks: for a lint, a rule whose `paths` cover the file; for a test, a case that reads that string. When in doubt it breaks the line, runs the command red and restores the line before it writes the entry. A survivor already filed is mended in its command when that command should read the line, as on 2026-11-27. When the command should not read it, the item goes up the ladder to its oracle.
