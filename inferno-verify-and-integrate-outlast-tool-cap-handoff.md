# Handoff: `verify-item` and `integrate` have no detach-and-wait form while `gate` and `review` do, so a call whose checks or real-app prove run past two hours outlasts the agent's tool call cap

Row 0bo. Met on the first host on Delta on 2026-11-24, 2026-11-25 and 2026-11-26, on the build installed there, `a8873ebb`. The tip `c38b8b1b` holds the same `src/`. Widened on 2026-11-27 from the first host's background-deadline oracle of 2026-11-26, which held it a handoff because the host has a workaround.

## What is wrong

`S/` below is `src/flows/inferno/agents/orchestrator/skills/orchestrate/scripts/`.

1. **Two long steps only block.** `verify-item` runs the item's own check and, on a host that sets `real_app.prove`, the real-app prove of the journeys the item changed (`proveItem`, the run at `S/run-real-app-prove.cjs:64`). `integrate --item` folds the base and runs every integrate command. Each returns only when its last command ends (usage `S/run.cjs:59-60` and `:71-73`).
2. **`gate` and `review` have the form.** `gate --detach` starts the gate as its own process, and `gate --wait` blocks at most `--minutes` (default 9) and exits 4 while it runs (`S/run.cjs:78`, `:83`, `:127`). `review --detach` and `review --wait` do the same for a record (`:67-68`, `S/run-review-job.cjs`). Only `S/run-gate*.cjs`, `S/run-review-job.cjs` and `S/run-snapshot.cjs` read `options.detach` or `options.wait`.
3. **The orchestrator calls run.cjs through a tool with a call cap.** A Claude Code Bash call ends at its timeout, two hours at most (7200000 ms on the first host). The tool then moves the call to the background and stops it later: two hours later on 2026-11-24, ten minutes later since 2026-11-26 (Evidence). A call the session starts in the background is stopped at two hours, a headless session can lose one when its turn ends, and the first host refuses `run_in_background` with a hook. So no tool call can hold a step that runs past two hours, and the orchestrate procedure names no other way to run it.
4. **The steps now run that long.** On the first host a real-app prove walks the item's journey files and their can-fail mutants on the real binary. Since the host's lane gives the machine lock to waiting runs between walks (`5ab96a3a5`), one prove of one journey file took 5926 s and another 7075 s. On 2026-11-25 the walk of one item took 10,837 s (3.0 h).

## How to fix

1. **`verify-item --detach` and `integrate --detach`.** Each starts the step as its own process in the tree through `S/run-jobs.cjs` (`detach()` `:81-101`, `alive()` `:41-54`), as `gate --detach` and `review --detach` do (`S/run-gate.cjs:295-302`, `S/run-review-job.cjs`). It writes the step's lines, payload and exit code where `--wait` reads them. A second `--detach` of the same step for the same item, or for the tree when `integrate` names no item, exits 2 while the first runs. `--detach --json` names the job's pid, as `gate --detach` does (`S/run-gate.cjs:300-301`), so a host can stop it. `verify-item --wait` and `integrate --wait [--minutes <n>]` block at most n minutes (default 9, as `gate --wait`). They exit 4 while the step runs, then print its lines and exit with its own code.
2. **A job that died reads as dead.** When the job is gone and left no result, `--wait` prints that it ended without a result, the log's last lines and the call that starts it again, and exits 5. The legend already gives 5 to a step with no verdict that runs again (`S/run.cjs:19`, `:139`). So a killed walk never reads as running, and never as a red a builder is sent to fix. Today `gate --wait` and `review --wait` read a died job as exit 2 (`S/run-gate.cjs:314-318`, `S/run-review-job.cjs:119-124`).
3. **The procedure names the pair.** `S/run-call.cjs` gets a start call and a wait call for each step beside `verifyItemCall` (`:98`), `integrateCall` (`:101`) and `integrateAgainCall` (`:104`). Every site that prints one of those prints the start call and then the wait call: `S/run-frontier.cjs:61`, `S/run-review.cjs:103`, `:187`, `:363`, `:399`, `S/run-item-proof.cjs:418`, `S/run-integrate.cjs:348`, `S/run-peers.cjs:200`, `S/run-gate-marks.cjs:55`, `S/run-mutant-coverage.cjs:156` and `S/state-transition.cjs:141`, `:191`. Wherever the orchestrator text runs `verify-item` or `integrate` (`orchestrator/agent.md:68`, `:76`), it runs `--detach` and then `--wait` until the exit is not 4. With it, row 0bu's integrate beside the reviews needs no host wrapper either.
4. **The tests.** Beside the tests of `verify-item` and `integrate`: give the host a check that sleeps past a `--wait` of a fraction of a minute. Then `--detach` returns at once and its `--json` holds the pid, `--wait` exits 4 while the check runs and afterwards exits with the step's own code and prints its lines, and a second `--detach` while one runs exits 2. A job killed with SIGKILL reads 5 at the next `--wait`, never 4. The tests of the printing sites read the start call and the wait call where they read the call today.

## The orchestrator's wait for a subagent

Added 2026-11-25 from the first host's stall oracle (its cause 6), on the same build. The orchestrator text names no wait for a subagent started in the background or resumed with a message. Neither `orchestrator/agent.md` nor `orchestrator/skills/orchestrate/SKILL.md` mentions `run_in_background`, a resumed agent or `SubagentHandback`. A subagent that hands back writes a `SubagentHandback` tool call and never an `end_turn`, so an orchestrator that waits for the turn to end reads the result late. The oracle measured the hand-backs of one session (techdoc) read 9 to 80 minutes after they were written.

Fix, with point 3 above: the orchestrate procedure dispatches builders and reviewers in the foreground where the tool allows it. After a background start or a message resume, it waits for the agent's hand-back, its `SubagentHandback` result, and never for an `end_turn`. That is one line in the orchestrator text, held by the role-text tests.

Meanwhile, sessions dispatch builders and reviewers with `run_in_background: false`. After a resume they wait for a new `"name":"SubagentHandback"` line in the agent's transcript (the first host's `~/.claude/scripts/agent-wait.py`).

## Until it is built

The first host's workaround, decided on 2026-11-26: a helper of its own, `~/.claude/scripts/intent-run.sh`, starts every `verify-item` and `integrate`, and any other command of a session that can run past ten minutes, as a detached run with its own log, pid and exit record. The session reads the run with the helper's `wait`, in the foreground and inside the hour, and a run that died without an exit reads as `KILLED`. A stop of the session ends every process that carries the session's mark. The wait on the log's closing line that stood here before cost 1.8 h on a dead log on 2026-11-26. No session wraps either step in a `timeout` shorter than the step. How long the prove takes on the first host (machine lock waits and yields, the walks of earlier items' mutants) is the host's concern, not this row's builder's.
